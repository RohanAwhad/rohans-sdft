## Session Write-up: CP=2 Implementation for OOM Fix

### The Problem
`sdft_gptoss_20b_smoke_len8192b` (recompute fix + `expandable_segments:True`) OOMs at `scaled_loss.backward()`, `trainer.py:432`:
- **What**: Attempting to allocate **6.14 GiB** on a GPU with 73.78 GiB allocated, 2.10 GiB free
- **Why**: The dense `(C, V)` fp32 gradient of student completion-logits — `C × 201088 × 4B` = 6.14 GiB at C=8192
- **Where**: The reverse-KL loss backward materializes a full fp32 grad buffer for the entire `forward_student` logits output, and that buffer hits the limit before optimizer states/params/activations even finish fitting
- **Why recompute didn't save it**: Unknown at start — `model.config.recompute_granularity='full'` was set but peak memory was still ~74GB per rank

### Diagnosis

**What the logits-grad buffer is**: `forward_student` (trainer.py:134-167) runs the model over `prompt(2048) + completion(C)` → `(1, P+C, V)` logits → slices completion positions → `(C, V)` tensor. In `compute_kl` (trainer.py:84-131), this is converted to fp32 per-chunk, and `loss = per_token_kl.mean()` triggers a backward that materializes a **dense `(C, V)` fp32 gradient** — the full completion-logits gradient, regardless of chunking in the loss forward.

**At 6144 completion**: the buffer becomes `6144 × 201088 × 4B = 4.94 GB` → still too large for the ~2 GB headroom. So the buffer must shrink (via CP splitting of the sequence dimension) **AND/OR** the baseline memory must drop (via actually-working recompute).

### Exploration: Context Parallel (CP=2 × DP=2)

User asked what parallelism types exist (DP, TP, PP, CP, EP, SP). We decided **CP=2 × DP=2** across the 4 trainer GPUs.

**Why CP fits this specific OOM**: CP splits the sequence dimension. At CP=2:
- Each rank processes `8192 / 2 = 4096` tokens → completion per rank ~3072 (uneven — see below)
- Logits-grad per rank: `C_rank × V × 4B` → ~2.5 GiB max instead of 4.9 GiB
- All intermediate activations (attention, MLP, residuals) also halve

### MCore 0.18.2 CP Internals (what we found reading bridge/MCore source)

- **Bridge provider**: `GPTModelProvider extends TransformerConfig` — has `context_parallel_size` field (default 1). Set via `provider.context_parallel_size = 2` after `to_megatron_provider()`, but better: `bridge.to_megatron_provider(load_weights=True)` then set on provider (or via env var — unresolved; mp_overrides only used in `load_megatron_model`, not `to_megatron_provider`)
- **Parallel state init**: `initialize_model_parallel` (model_provider.py:287) calls `parallel_state.initialize_model_parallel(context_parallel_size=getattr(self, "context_parallel_size", 1))` → bridge handles CP group creation
- **TransformerLayer CP**: `config.cp_comm_type="a2a"` (Ulysses all-to-all) is read at forward time and passed to TE fused attention, which does the CP cross-rank key/value exchange automatically
- **Input contract**: **Pre-split** — each CP rank feeds its own contiguous chunk `input_ids[cp_rank*S/CP : (cp_rank+1)*S/CP]` and `position_ids` slice. The attention mask (when None) gets resolved to `(B, 1, slen_per_cp, S)` by the layer — causal, but query-dim = local chunk, KV-dim = full sequence
- **FSDP + CP**: `TorchFullyShardedDataParallel` uses `get_data_parallel_group(with_context_parallel=True)` → **FSDP mesh includes CP dimension** — params/grads are sharded across DP×CP (all 4 ranks). So FSDP's `finish_grad_sync` already covers the full world → **global mean gradient is correct** without manual CP-group allreduce
- **Loss scaling**: With FSDP covering DP×CP, per-rank loss should be scaled by `C_rank / C_total` (uneven chunk weight) and `CP_SIZE` (to compensate FSDP sum semantics): `scaled_loss = (loss * C_rank / total_C * CP_SIZE) / local_accum_steps`

### Completion Slice Math
Uneven chunks when P isn't aligned to slen_per_cp. For P=2048, C=6144, S=8192, CP=2, slen_per_cp=4096:
| Rank | Chunk range | Completion intersection | C_rank |
|------|-------------|------------------------|--------|
| 0    | [0, 4096)   | [2048, 4096)           | 2048   |
| 1    | [4096, 8192) | [4096, 8192)          | 4096   |

Each rank slices `logits` (local, (slen_per_cp, V)) and `teacher_log_probs` (global, (C, V)) accordingly.

### 2-GPU Experiment (cp_test.py)
- **CP forward**: **PASSED** — model loads with CP=2, pre-split input (1, 4096) per rank → logits shape `(4096, 201088)` (2D, batch squeezed) → completion slices correct (rank0: 2048 rows, rank1: 4096 rows)
- **CP backward**: **OOM** — `~77 GB allocated` on each rank, trying 508 MiB allocation at `kl.backward()`
- **Conclusion**: CP=2 alone does **not** bring memory low enough. The peak is ~77 GB — same order of magnitude as CP=1 at similar sequence length. CP halves activation memory per rank, but with 61 layers × 4096 tokens, materialized activations still dominate (~25-30 GB). **Recompute MUST be active** to drop that to ~2 layers' worth (~2-3 GB)

### Why Recompute Isn't Working (hypothesis)

`model_utils.py:118-120` sets `model.config.recompute_granularity = 'full'` on the built model. MCore's `TransformerLayer.forward` reads this at call time. Possible reasons it's a no-op:

1. **gpt-oss uses a custom layer** (GptOssDecoderLayer or similar) that overrides `forward` and doesn't respect `self.config.recompute_granularity`
2. **FSDP wrapping** (`TorchFullyShardedDataParallel`) may interfere with `torch.utils.checkpoint` inside the layer
3. **Recompute is on but has minimal effect** because the logits-grad buffer (output-level, not layer-level) dominates memory — but 77 GB peak > 42 GB model + 5 GB output → ~30 GB of layer activations, which recompute should compress to ~2 GB. So recompute ISN'T reducing layer activations — it's truly not working
